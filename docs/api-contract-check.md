## Frontend changes completed (this task)

- **Password reset email link** now carries both `uid` and `token` query parameters. The `/reset-password` page reads both from the URL and sends `uid`, `token`, `new_password`, `new_password_confirm` to the backend.
- **Removed the "uid as token placeholder" workaround** that was previously in the frontend (test `uses the backend email uid as the required placeholder token when no token is present` was removed).
- **Email verification flow page** (`/verify-email`) added, reads `token` from URL query params, calls `POST /auth/verify-email/`, shows loading/success/error states.
- **Token refresh with rotation** implemented: backend returns new refresh token on each refresh; frontend stores the rotated refresh token; handles blacklisted/expired refresh (400/401) by logging out cleanly (clearing local session and notifying listeners).
- **Logout** posts the current refresh token to the backend for blacklisting, then clears local state.
- **Access token lifetime** is 15 minutes; single-flight refresh before expiry on 401 is already present and verified working.
- **Registration response shape** and error field names match the backend contract (returns `detail` only, no tokens; field errors for `email`, `password`, `password_confirm`).
- **Throttling 429** shows `Retry-After` message via the `ApiError.retryAfter` field; dispatched as `api-http-failure` event.
- **MSW mocks** updated in `src/mocks/handlers.ts` and `src/mocks/auth.ts` to match backend contract.
- **OpenAPI snapshot** regenerated from hardened backend (`src/mocks/openapi.snapshot.json`).
- **Tests** updated for all auth pages: `ResetPasswordPage`, `ForgotPasswordPage`, `RegisterPage`, `LoginPage`, `VerifyEmailPage`, and `auth.test.ts`.

## Backend notes (for reference)

- Password reset emails from the backend include both `uid` (base64-encoded user PK) and `token` (Django's `default_token_generator`) as query parameters in the reset link.
- Registration returns only a detail message after sending email verification, so the frontend cannot establish an authenticated session until login. The frontend now reflects that behavior.
- The generated OpenAPI schema omits request/response detail for several `APIView`s (including auth, alert preferences/unsubscribe, and review summary/helpful operations) because schema introspection cannot infer serializers. Route/method checks cover operations present in the snapshot; payload tests and backend serializer/view inspection cover these omitted details.
- The review serializer exposes `reviewer_name`, `created`, and `modified`; it does not expose user identity, moderation status, or the current user's vote. Approved list entries therefore cannot support a verified-cardholder claim or ownership actions. New submissions are saved pending moderation, which is communicated only in the submission confirmation.
